# Логи сервера: сбор, фильтрация, выгрузка

Дизайн от 2026-08-30. Реализация — `docs/logging-plan.md`.

## Задача

Сейчас у серверного стека (`server/stream`) логов фактически нет:

- панель (`panel/server.js`, 1647 строк) пишет один `console.log` на старте; ошибки
  Docker/OBS/fetch уходят в HTTP-ответ клиенту и исчезают;
- фронт (`panel/public/app.js`) не логирует ничего;
- логи сервисов живут только внутри Docker (`docker logs`), их объём ничем не ограничен;
- эндпоинт `GET /api/containers/:name/logs` (SSE, `tail 200`) есть, но UI использует его
  только для сборки/энроллмента субтитров; скачать или переслать лог нельзя.

Одновременно логи зашумлены. Главный источник — SRS: при `srs_log_tank console` он каждые
5 секунд пишет строку `Hybrid cpu=..., timer=...` вечно, даже когда эфира нет. Понизить
уровень нельзя: полезные события (публикатор подключился/отключился) SRS пишет тем же
уровнем `trace`.

Нужно: писать логи, уметь отдать их одним файлом для пересылки, вырезать повторы.

## Решение

Панель — единый коллектор. Она подписывается на docker-логи всех сервисов, прогоняет
строки через фильтр и пишет их в один файл вместе со своими событиями. Так фильтр живёт в
одном месте, а события разных сервисов выстраиваются в общую хронологию — это главное при
расследовании («телефон отвалился → что в этот момент сказал srtla-rec → что SRS»).
Сами srs/srtla-rec при этом не трогаем.

Слабое место подхода — пока панель не поднялась, коллектор молчит. Компенсируется тем, что
при выгрузке мы дополнительно добираем хвост напрямую из Docker (см. «Выгрузка»).

Отвергнутые варианты:

- **каждый сервис пишет в файл сам** — фильтр шума ставить негде (SRS так не умеет), нет
  общей хронологии, собирать надо из пяти мест;
- **сборщик на PowerShell рядом со `start.bat`** — работает и без панели, но это лишнее
  окно и процесс, а события самой панели попадут туда только как неструктурированный текст.

Из отвергнутого варианта берём одну деталь: ограничение размера докеровских логов
(`logging.options.max-size`), иначе json-file растёт на диске неограниченно.

## Компоненты

### 1. Хранилище

Папка `logs/` рядом со `start.bat`: в репо — `server/stream/logs/`, у установленной копии —
`%localappdata%\BondcastStream\logs\`. Панель получает её bind-монтированием
(`./logs:/logs` в `docker-compose.yml`), путь внутри контейнера — `/logs`.

Файл `bondcast.log`. Ротация по размеру: при достижении 5 МБ файл переименовывается в
`bondcast.1.log` (существующий `bondcast.1.log` сдвигается в `bondcast.2.log`, бывший
`bondcast.2.log` удаляется). Итого на диске максимум три файла и ~15 МБ.

`logs/` добавляется в `server/stream/.gitignore`.

### 2. `panel/logger.js`

Новый модуль, не знающий про express. Публичный интерфейс:

- `log(service, level, message)` — уровни `debug` / `info` / `warn` / `error`;
- `tail(n)` — последние строки из кольцевого буфера;
- `subscribe(fn)` / `unsubscribe(fn)` — для SSE живого просмотра;
- `readFiles()` — содержимое `bondcast.log` и ротированных, для выгрузки.

Формат строки — единый для панели и для сервисов, grep-совместимый:

```
2026-08-30 14:03:11.482  WARN   srs    SRT connect failed, streamid=bondcast/live/foo
```

Каждая строка пишется одновременно в файл и в кольцевой буфер в памяти (последние 2000
строк) — из буфера живёт просмотр в UI, без чтения файла на каждый запрос.

Уровень по умолчанию — `info`. `debug` включается переменной окружения `LOG_LEVEL=debug`
(прокидывается через `docker-compose.yml`).

`panel/Dockerfile` сейчас копирует только `server.js` (`COPY server.js ./`) — новый модуль
и его тест нужно добавить в COPY, иначе образ соберётся без них.

### 3. Сбор логов сервисов

При старте панель подписывается на `container.logs({ follow: true, tail: 0 })` для `srs`,
`srtla-rec`, `overlay`, `asr-worker` (последний — только если контейнер существует, он
поднимается лениво по кнопке). Подписка восстанавливается по docker events, когда
контейнер перезапустился или был пересоздан.

`tail: 0`, а не `tail: N`: старые строки уже были собраны прошлой подпиской, иначе после
каждого рестарта в файл попадёт дубль хвоста.

### 4. Фильтр — два шага

**Шаг 1, чёрный список.** Массив регулярок в `logger.js`, у каждой — комментарий, почему
эта строка мусор. Стартовый набор:

- SRS `Hybrid cpu=...` — периодическая телеметрия каждые 5 с, идёт даже без эфира;
- периодическая статистика SRS по соединению (те же 5 с на публикатора);
- keepalive-строки `srtla_rec`;
- `200 OK` от nginx-оверлея на статику (`.html`, `.js`, `.css`).

**Шаг 2, схлопывание.** Строка нормализуется (все числа → `#`), и если нормализованная
форма совпадает с предыдущей — строка не пишется, а копится счётчик. Накопленное
выводится одной строкой при смене строки или по таймауту 60 с:

```
2026-08-30 14:05:11.004  WARN   srtla-rec  … предыдущее сообщение ×47 за 1м20с
```

Это ловит повторы, которых нет в чёрном списке — например одну и ту же ошибку, сыплющуюся
пачкой.

### 5. Что логирует сама панель

Не всё подряд, а следы, по которым потом восстанавливают картину:

- старт / стоп / пересоздание контейнеров — что запросили, чем кончилось;
- любая ошибка docker / fetch / OBS-websocket — с текстом ошибки;
- проверка достижимости порта (`/api/reachability`) и её вердикт;
- жизненный цикл субтитров: сборка образа, connect, disconnect, энроллмент голоса;
- появление и пропажа публикатора в SRS (панель уже опрашивает `getActiveSrsStreams`);
- ход тихого обновления (`POST /api/update/progress`);
- каждый ответ 5xx — одной строкой, через обёртку над express.

Частые GET-опросы фронта (`/api/streams` и соседи, несколько раз в секунду) **не**
логируются даже на уровне `debug`: иначе панель сама станет главным источником повторов,
ровно тем, что эта работа устраняет.

### 6. Ошибки фронта

`window.onerror` и `unhandledrejection` в `app.js` шлют `POST /api/logs/client`
(`{ message, stack, url }`). Панель пишет их в тот же файл под именем сервиса `ui`.
Это ловит случай «у меня панель просто белая», который сейчас не виден вообще никак.

Эндпоинт за общей авторизацией (`app.use(auth)`), сообщение обрезается до 2000 символов,
принимается не больше 20 сообщений в минуту — иначе цикл ошибок в браузере зальёт файл.

### 7. Выгрузка

`GET /api/logs/bundle` отдаёт **один `.txt`** с `Content-Disposition: attachment`,
имя вида `bondcast-logs-2026-08-30-1403.txt`. Zip не используем — не нужна новая
зависимость, а один текстовый файл проще переслать и открыть.

Состав:

1. **шапка** — версия установки (`/build-context/VERSION`), текущее время, версия Docker,
   статус всех контейнеров, проброшенные порты, `HOST_IPS` / `LAN_IPS` / `GATEWAY_IPS`;
2. **`bondcast.log`** целиком; если он меньше 1 МБ, перед ним добавляется `bondcast.1.log` —
   иначе сразу после ротации в выгрузке окажется почти пустой лог;
3. **хвосты `tail 500`** докеровских логов каждого сервиса напрямую — страховка на случай,
   если коллектор что-то пропустил или панель стартовала позже сервисов.

В шапку **не попадают** `PANEL_PASS`, `PANEL_USER` и `NOALBS_STATS_TOKEN`: файл пересылают
посторонним. Значения заменяются на `(задан)` / `(пусто)`.

### 8. UI

- **Кнопка «Скачать логи»** — видна всем, обычная ссылка `<a href="/api/logs/bundle" download>`
  в карточке помощи.
- **Вкладка «Диагностика»** — скрытая: появляется, если в адресе есть `#debug`, и после
  этого запоминается в `localStorage`. Внутри: живой лог по SSE (`GET /api/logs/stream`),
  фильтр по сервису и по уровню, поиск по подстроке, пауза, очистить, та же кнопка скачивания.
  Обычным пользователям вкладка не показывается — им хватает кнопки.
- Заодно чинится текст в `panel/public/app.js:503`, который сейчас отправляет пользователя
  на вкладку «Функции» → «Диагностика», которой не существует.

### 9. Ограничение докеровских логов

Каждому сервису в `docker-compose.yml`:

```yaml
logging:
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"
```

Сейчас лимита нет вообще, и на долгом эфире json-file растёт неограниченно. Это отдельная
от нашего файла защита: она страхует случай, когда панель не работает и коллектор молчит.

## Потоки данных

```
srs        ─┐
srtla-rec  ─┤  docker logs (follow)
overlay    ─┤          │
asr-worker ─┘          ▼
                чёрный список → схлопывание ─┐
                                             ├─→ bondcast.log (ротация 5 МБ × 3)
события панели ──────────────────────────────┤
POST /api/logs/client (ошибки фронта) ───────┤
                                             └─→ кольцевой буфер (2000 строк)
                                                        │
                                     GET /api/logs/stream (SSE) → вкладка «Диагностика»
                                     GET /api/logs/bundle → .txt + хвосты из Docker
```

## Обработка ошибок

- Папка `/logs` недоступна на запись (bind не смонтирован при запуске из репо без
  пересборки) — панель пишет об этом один раз в `stdout` и продолжает работать только с
  кольцевым буфером. Отсутствие логов не должно ронять панель.
- Контейнер, на который подписан коллектор, удалён — подписка закрывается, ошибка
  логируется на уровне `debug`, повторная подписка происходит по docker events.
- Ротация не смогла переименовать файл (файл открыт антивирусом) — пишем дальше в текущий,
  ошибку логируем один раз, чтобы не зациклиться.
- `GET /api/logs/bundle` не смог достучаться до Docker — секция с хвостами заменяется
  строкой об ошибке, остальной файл всё равно отдаётся.

## Тестирование

Автоматически (`node --test`, встроенный раннер, без новых зависимостей),
`panel/logger.test.js`:

- строка из чёрного списка не попадает в вывод;
- строка не из списка попадает;
- три одинаковых строки подряд дают одну запись со счётчиком `×3`;
- строки, отличающиеся только числами, считаются одинаковыми (нормализация);
- смена строки выталкивает накопленный счётчик;
- ротация: при превышении лимита создаётся `bondcast.1.log`, файлов не больше трёх.

Руками, на живом стеке:

1. `docker compose up -d --build panel` из `server/stream`;
2. час эфира с телефона — в `logs/bondcast.log` должны быть сотни строк, а не десятки тысяч;
3. кнопка «Скачать логи» — файл открывается, читается, паролей внутри нет;
4. `#debug` — вкладка «Диагностика» показывает живой лог, фильтры работают;
5. `docker restart srs` — коллектор переподписался, строки SRS снова идут в файл.

## Границы работы

Не входит: отправка логов куда-либо автоматически, ярлык «открыть папку с логами» через
URL-протокол (механизм в проекте есть — `bondcast-obs:`, `bondcast-update:`, — но кнопки
скачивания достаточно), логирование в самом Android-приложении.
